`Tooltip` and `Popover` no longer schedule a state update when the element they are attached to mounts, unmounts, or is hidden and shown again by an `<Activity>`. The ref callback the cloned child receives used to set the element into state (the tooltip's own, and Floating UI's through its `refs.setReference`), which React schedules at Immediate priority as it runs in the commit phase. Inside a React 19.3 `<ViewTransition>` such an update is committed as soon as the transition that reveals (or hides) the element is ready to animate, right before its first frame, which held the animation up by the re-render of every tooltip and popover in the revealed tree, and left a pending sync update that made React skip the transition should anything flush sync work while the browser was still preparing it (a `flushSync`, or React restoring the value of a controlled input).

The element now lives in a ref. Floating UI is handed it when the card it positions mounts, which is when the tooltip is shown or the popover opens, so the update it schedules for the element rides along with the one for the card; a popover's intent listeners (which pre-render it when the pointer enters, presses or focus lands on its reference) are attached from the same ref callback. The child's own `ref` is attached from that callback as well, so it holds the element from the commit that mounts it on, where it was set one render later before. Mounting a closed tooltip or popover takes one commit instead of two.
