`MenuButton` composes the `onClick`, `onKeyDown` and `onMouseDown` handlers on its `button` element, and the `onBlurCapture`, `onClick` and `onClickCapture` handlers on its `menu` element, with its own instead of replacing them. A handler on the button element runs first, and one that calls `event.preventDefault()` keeps `MenuButton` from acting on that event: a click or key press whose default is prevented does not toggle the menu, and `MenuButton` leaves the default of a press on the button of an open menu alone. That includes a handler that prevents the default for its own reasons, such as the navigation of an `<a>` used as the button or the submission of a `type="submit"` button, which now also keeps the menu from opening. Handlers on these elements used to be dropped silently. `MenuProps['onBlurCapture']` is typed as the React `FocusEventHandler<HTMLDivElement>` the element delivers, instead of a handler of the DOM `FocusEvent`. An `onClick` on the button element runs for pointer clicks only: `MenuButton` prevents the default of the key presses that open the menu, so the browser synthesizes no click for them.

`onOpen` and `onClose` are now called from the event that opens or closes the menu, before the new state is committed, instead of from an effect after the commit that rendered it. State set in those callbacks commits together with the menu's own open state, and a callback that moves focus does so before the browser paints the open or closed menu. Each callback is still called once per change, including when closing moves focus back to the button, and focus is returned to the button before `onClose` is called, so focus that `onClose` moves elsewhere stands, as it did before. That holds for a menu item click even when the item's own `onClick` moves focus out of the menu: the blur that causes no longer closes the menu on its own, the item click does, with focus returned to the button first. Two consequences of the callbacks running in the event rather than in an effect: an error thrown in them no longer reaches an error boundary (a thrown `onOpen` is reported through the window's `error` event, like any error in a transition, and the menu still opens; a thrown `onClose` is thrown from the closing event, or from the task right after it in the one case where the close itself runs there: a click inside the menu whose handler stopped the click's propagation and moved focus out of the menu), and on a first open without prior intent the menu is not in the DOM yet when `onOpen` runs, so anything that measured or focused the menu from `onOpen` belongs in an effect.

`MenuButton` opens in a React transition and closes synchronously. `Popover` pre-renders the closed menu once the button shows intent to open it, and an open that arrives while that pre-render is still in progress now continues it instead of rendering the menu synchronously in the event; `onOpen` runs inside that transition, so state set in it commits with the open state (an urgent update from it needs `flushSync`). Closing only hides the menu, so it stays a synchronous update and commits together with whatever else the closing event updated, such as a dialog that a menu item opens. Menu content that suspends keeps the open pending until it can render, with nothing shown and the button still reporting the menu closed; wrap such content in a `Suspense` boundary to show a fallback. A click on the button in the meantime requests the opposite of the pending open and closes it, and Escape or a click outside cancel it, as they would close an open menu. Tests that drive `MenuButton` through `@testing-library`'s `fireEvent` or `userEvent` are unaffected, since both flush transitions; tests that dispatch DOM events directly need to wait for the open to commit before reading the open state, by polling for the state they expect rather than waiting a fixed number of frames.
