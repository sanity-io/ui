`MenuButton` composes the `onClick`, `onKeyDown` and `onMouseDown` handlers on its `button` element with its own instead of replacing them. A handler on the button element runs first, and one that calls `event.preventDefault()` keeps `MenuButton` from acting on that event: a click or key press whose default is prevented does not toggle the menu, and `MenuButton` leaves the default of a press on the button of an open menu alone. Handlers on the button element used to be dropped silently.

`onOpen` and `onClose` are now called from the event that opens or closes the menu, before the new state is committed, instead of from an effect after the commit that rendered it. State set in those callbacks commits together with the menu's own open state, and a callback that moves focus does so before the browser paints the open or closed menu. Each callback is still called once per change, including when closing moves focus back to the button, and focus is returned to the button before `onClose` is called, so focus that `onClose` moves elsewhere stands, as it did before. That holds for a menu item click even when the item's own `onClick` moves focus out of the menu: the blur that causes no longer closes the menu on its own, the item click does, with focus returned to the button first.

`MenuButton` updates its open state in a React transition. `Popover` pre-renders the closed menu once the button shows intent to open it, and an open that arrives while that pre-render is still in progress now continues it instead of rendering the menu synchronously in the event. `onOpen` and `onClose` run inside that transition. Tests that drive `MenuButton` through `@testing-library`'s `fireEvent` or `userEvent` are unaffected, since both flush transitions; tests that dispatch DOM events directly need to wait for the transition to commit before reading the open state, by polling for the state they expect rather than waiting a fixed number of frames.
